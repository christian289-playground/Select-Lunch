# 투표 인원에 따른 식사 기록

개인별 투표는 한 곳, 실제 식사 기록은 한 곳 이상이다. 투표 마감 결과와 앱 추천은 바꾸지 않는다. 여러 곳을 가야 하는 것이 아니라 여러 곳을 기록할 수 있게 하는 변경이다. 별도로 출발 전 식당을 확정하거나 사람을 식당에 배정하지 않는다.

## 한도

`Lunch:MealParticipantsPerRestaurant`는 양의 정수이며 기본값은 5다. 같은 채널·날짜의 마감된 본투표에서 식당을 고른 사람 수를 사용한다. 비밀·랜덤·본투표에 반영된 사전표도 각 한 사람으로 센다. 따로 먹는 사람·미응답자는 제외한다. 투표 행과 사전투표 행을 합산하지 않는다. 미리 출발 알림의 인원 설정은 별개다.

최대 확정 수는 `max(1, ceil(식당 투표 인원 / 기준 인원))`이다. 마감된 투표가 없거나 식당표가 없어도 기존처럼 실제로 간 한 곳은 기록할 수 있다. 기준 5에서 5·6·10·11명은 각각 1·2·2·3곳, 기준 4에서 4·5명은 1·2곳이다. 선택 수는 1부터 최대까지이며 저장할 때도 현재 한도를 검사한다. 한도 변경으로 초과하면 일부만 잘라 저장하지 않는다.

## 입력과 저장

- 입력 위치는 오후 **‘뭐 드셨어요?’** 메시지다. 이미 게시한 버튼·검색 선택의 식별자를 계속 사용한다. 미확정 상태에서 한 식당을 고르면 그 식당을 미리 담은 본인용 확정 창을 연다. 상호·종류로 다른 식당을 찾아 추가하거나 하나만 남기고 저장한다. 당일 정정은 기록된 전체 목록에서 시작한다. 열기·검색·취소는 식사 기록을 쓰지 않는다.
- ‘새 식당 등록’으로 기록할 때도 새 식당 하나와 선택 사항인 기존 식당들을 같은 한도 안에서 함께 확정할 수 있다. 날짜 또는 선택이 거절되면 식당 등록만 따로 남기지 않는다. 일반 식당 등록·수정 명령의 의미는 바뀌지 않는다.
- 식사 기록의 고유키만 `(채널, 날짜)`에서 `(채널, 날짜, 식당)`으로 바꾼다. 기존 행과 기록자·시각·출처를 보존한다. 날짜·채널·대상 식당과 한도를 서버에서 검증한 뒤 선택 목록 전체를 한 트랜잭션으로 저장한다. 잘못된 선택·중복·일부만 저장하는 결과를 허용하지 않는다. 당일에는 다시 확정해 전체 목록을 정정할 수 있다.
- 확정 안내와 다음 기록 요청은 저장된 전체 식당을 표시한다. 각 식당은 해당 날짜의 방문 1회로 추천 이력에 반영된다. 서로 다른 두 식당이 같은 카테고리면 해당 카테고리 방문은 2회다. 마감된 투표와 그때의 점수 설명은 바꾸지 않는다.

## 이미 올라온 미확정 요청

배포 대상은 구성 채널에 이미 올라온 **11월 19일 식사 기록 요청**이다. 채널 메시지를 삭제·교체·재게시하지 않고 기존 선택 동작으로 확정 창을 연다. 배포 자체로 선택을 저장하거나 사람에게 대신 투표하지 않는다.

일반적인 과거 기록 잠금은 유지한다. 운영에서만 `Lunch:CarryoverMealPromptDate`로 지정한 한 날짜(기본 미지정)에 한해, 구성 채널에 기록 요청을 게시한 이력이 있고 그날 식사 기록이 아직 없을 때 최초 확정을 허용한다. 창을 연 뒤 다른 사람이 먼저 저장해도 과거 기록을 덮어쓰지 않도록 제출 트랜잭션 안에서 재검사한다. 이 예외로 다른 날의 열린 투표나 출발 알림을 변경하지 않는다.

## 검증과 배포

경계 인원·설정값 변경·기권/비밀표·무투표, 한 곳만 확정, 여러 곳의 원자적 저장과 당일 정정, 구형 버튼/검색/등록, 취소, 지난 미확정 요청의 최초 저장과 두 번째 제출 거절을 검증한다. 기존 데이터가 있는 DB에 마이그레이션을 적용해 보존과 복수 식당 집계를 확인한다. 운영 백업·배포·기동 검증은 기존 배포 절차를 따른다. 실제 슬랙 검증은 확정 창의 한도와 초기 선택을 확인하고 취소하는 데서 끝낸다. 운영 식사 기록을 검증용으로 만들지 않는다.
